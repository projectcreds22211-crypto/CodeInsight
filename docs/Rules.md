## 1. Tool Assignment Rules

CodeInsight is built across three AI tools with different strengths. Assign work accordingly — do not let a tool freelance outside its lane.

| Tool                     | Use for                                                                                                                     | Do NOT use for                                                                       |
| ------------------------ | --------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| **Antigravity (Gemini)** | Boilerplate scaffolding, UI component structure, Tailwind styling, CRUD routes, polish passes                               | Core parsing/algorithmic logic (Code/DB/Log analyzers), correlation prompt design    |
| **Codex**                | AST parsing (`ts-morph`), SQL parsing/rules, anomaly detection logic, cycle detection, anything requiring exact correctness | Freeform UI generation without Design.md reference, creative copy                    |
| **Kimi**                 | Synthetic test data/fixtures, edge case brainstorming, docs, code comments pass                                             | Core algorithmic logic, security-sensitive code (auth middleware, DB access control) |
| **Claude (you, direct)** | Correlation Engine prompt/orchestration design, architecture decisions, cross-cutting review                                | —                                                                                    |

**Rule:** if a task touches `src/analyzers/*/[parser|rules|detection].ts`, it goes to Codex, full stop — these are the credibility-critical, deterministic-correctness files referenced in PRD Section 5 and must not be "vibe"-generated by a tool optimized for plausible-looking code over correct code.

## 3. Coding Style & Conventions

### General

- TypeScript strict mode on, in all monorepo packages, no exceptions.
- Function/variable naming: descriptive, no abbreviations except well-known ones (`db`, `req`, `res`, `id`). `analyzeCodebase()`, not `analyzeCB()`.
- File naming: kebab-case (`dependency-graph.ts`), component files PascalCase (`FindingCard.tsx`).
- No `any` type without an inline comment explaining why it's unavoidable.

### Comments (locked: comment non-obvious logic only, skip boilerplate)

- **Do comment:** parsing rules and their rationale, the correlation grounding mechanism (why a claim maps to a `finding.id`), anomaly detection thresholds and why they were chosen, any deliberate deviation from an obvious approach.
- **Don't comment:** what a getter does, what a standard React component renders, restating the function name in prose.

### Commits (locked: Conventional Commits)

```
feat: add SQL N+1 detection rule
fix: correlation engine crashes on empty findings array
chore: update Drizzle schema for findings table
docs: update Memory.md with Phase 2 completion
refactor: extract shared Claude client into service
```

Every commit message should make sense read on its own, without opening the diff.

## 4. Error Handling & Shared Analyzer Contracts

### Shared Platform Contracts

- All analyzers (Code, Database, Logs) must import and implement the shared domain contracts exported from `packages/shared-contracts`.
- **Single Finding Model:** Every finding produced by any analyzer must adhere strictly to the shared `Finding` model (`id`, `sessionId`, `category`, `severity`, `title`, `description`, `metadata`). No custom or ad-hoc finding shapes are permitted.
- **Single Severity Model:** All analyzers must use the unified `Severity` enum (`low`, `medium`, `high`, `critical`).
- **Single AnalyzerResult Model:** Every analyzer execution must return the standardized `AnalyzerResult` container payload comprising `sessionId`, `status`, `findings`, `summary`, `metrics`, and `Evidence[]`.
- **Non-Divergence Rule:** Analyzer outputs against the ground-truth benchmark dataset (`codeinsight-demo-repo`) must remain strictly deterministic and match `docs/EXPECTED_FINDINGS.md`. Analyzer logic must never produce divergent, non-deterministic, or missing findings across runs.

### Error Boundaries & Handling

- Every analyzer function returns a discriminated result, never throws past its own boundary:
  ```typescript
  type AnalyzerResult<T> =
    { status: 'success'; data: T } | { status: 'error'; message: string; recoverable: boolean };
  ```
- API routes never leak raw error stack traces to the client — return a clean `{ error: string }` shape, log the full error server-side.
- Frontend never shows a blank/broken state on failure — every async view has an explicit error state with a plain-language explanation (per Design.md Section on writing: "errors don't apologize, and they are never vague about what happened").
- Repo cloning, SQL parsing, and log parsing must each fail gracefully and independently — one analyzer failing must never block the other two from completing.

## 5. Security Rules

- No credentials, API keys, or secrets ever committed — `.env` files gitignored across all packages from the first commit.
- Auth: every non-webhook API route requires Clerk JWT verification in the `onRequest` hook — no route is "temporarily unprotected" during development.
- All project/finding/report queries scoped by `userId` derived from the verified JWT — never trust a client-supplied user ID.
- Cloned repositories: read-only, shallow clone, sandboxed to a temp directory, deleted in a `finally` block regardless of success/failure — no persistent filesystem state (Architecture.md Section 7).
- No arbitrary code execution from analyzed repositories — parsing only (AST inspection), never `eval`, never running the cloned repo's own scripts/build commands.
- Rate limit `/analyze/*` endpoints and cap accepted repo size (exact caps to be set in Phase 1 based on real testing — flag if none exist yet).

---

## 6. Performance Rules

- Repo clones: shallow (`--depth=1`) always, no full git history ever needed.
- Claude API calls: batch reasoning where possible, never issue redundant calls for data already fetched in the same session (cost discipline, per PRD Section 6).
- Correlation Engine must stream (SSE) — never make the user wait on a single blocking request for the full reasoning pass.
- Findings queries paginate/limit results rather than returning unbounded result sets to the frontend.

## 7. Design System Enforcement (from Design.md)

- Analyzer identity colors are locked and must be used consistently everywhere an analyzer is referenced (tabs, graph nodes, badges, The Thread): Code = `--analyzer-code` (`#6B4CE6`), Database = `--analyzer-db` (`#2E9C8F`), Logs = `--analyzer-logs` (`#D98E3B`). No tool may substitute a different color for these without flagging it explicitly.
- `theme-marketing` (cream) is used only on landing/auth/empty-state surfaces. `theme-app` (neutral) is used inside the authenticated dashboard. Do not apply the full cream background behind dense data views (React Flow graphs, findings tables) — this was a deliberate legibility decision, not an oversight.
- No serif fonts, no terracotta accent color, no stock illustrations, no decorative numbered markers unless the content is genuinely sequential — see Design.md Section 11 for the full "avoid" list.
- The Thread is the only animated signature element. No new decorative animations without checking Design.md Section 8 first.

## 8. Testing (locked: Vitest + React Testing Library)

- MVP testing scope, in priority order:
  1. Deterministic analyzer logic (SQL rules, anomaly z-score detection, cycle detection) — these are the credibility-critical functions, they get real unit tests matching `EXPECTED_FINDINGS.md`.
  2. Correlation grounding — a test verifying every `actionPlan` item's `referencedFindingIds` actually exist in the findings passed to that session.
  3. Core UI flows (create project, run an analyzer, view findings) — lighter-touch component/integration tests.
- Not required for MVP: full coverage of styling/presentational components, exhaustive edge-case coverage on every UI branch.

## 9. File Organization

- Follow the folder structures defined in Architecture.md Section 2 exactly — do not introduce new top-level folders without flagging it first.
- Each analyzer's `prompt.ts` stays colocated with that analyzer's own logic (Architecture.md's locked decision) — never centralize all prompts into one shared file.
- `docs/` folder (PRD, Architecture, Design, Rules, Phases, Memory, EXPECTED_FINDINGS) is maintained in the monorepo root and must be kept in sync across all documentation references.

## 10. The "Flag, Don't Block" Boundary (locked: moderate strictness)

The AI tool should proceed autonomously on most implementation work, but must **flag and summarize** (not silently do, and not fully block on) the following, appending a note to Memory.md and calling it out at the end of the session:

- Any change touching authentication logic or Clerk configuration
- Any change to the database schema (new tables, columns, migrations)
- Any change to deployment configuration (env vars, build settings, Render/Vercel config)
- Adding a new npm dependency not on the approved list (Section 2) — this one is **strict**, wait for explicit approval, don't just flag-and-proceed
- Any deviation from the folder structure or naming conventions in this document

Everything else — implementing a planned feature from Phases.md, fixing a bug, writing a component matching Design.md — proceeds without needing a check-in.

---

## 11. What the AI Should NEVER Do

- Never commit secrets, API keys, or `.env` files.
- Never add a rejected library from Section 2's exclusion list.
- Never let one analyzer's failure crash the other two.
- Never construct ad-hoc or custom finding shapes that bypass `packages/shared-contracts`.
- Never allow analyzer outputs to diverge from `docs/EXPECTED_FINDINGS.md` ground-truth benchmark baseline across execution runs.
- Never present a Claude-generated correlation claim that isn't traceable to a `finding.id`.
- Never apply `theme-marketing`'s full cream background to a data-dense dashboard view.
- Never introduce global state management outside React Context + TanStack Query.
- Never execute code from a cloned/analyzed repository.
- Never skip updating Memory.md at the end of a session (Section 13).

## 12. End-of-Session Protocol

Every coding session, regardless of which tool ran it, ends with:

1. A summary of what was completed.
2. Any flagged items from Section 10.
3. An update appended to `Memory.md` (completed features, decisions made, known bugs, next starting point) — this is not optional, it's how the next session (possibly a different tool) avoids re-deriving context from scratch.
